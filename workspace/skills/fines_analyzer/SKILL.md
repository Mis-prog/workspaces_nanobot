# Аналитика штрафов

Данные лежат в Greenplum, доступ только на чтение. SQL пишешь ты сам,
последовательно: запрос → результат → следующий запрос с учётом увиденного.

## Как выполнять запросы

```bash
# Колонки и типы (вызывай ДО первого запроса, если не знаешь схему)
./fines_analyze.sh --mode schema

# Выполнить SELECT
./fines_analyze.sh --mode query --sql "SELECT count(*) FROM <SCHEMA>.<TABLE>"

# Нарисовать график по результату запроса
./fines_analyze.sh --mode chart --sql "SELECT ... GROUP BY 1 ORDER BY 1" \
    --chart-type line --title "Динамика штрафов"
```

На Windows — `fines_analyze.bat` с теми же аргументами.

Скрипт проверяет запрос до выполнения и отклоняет всё, кроме одного SELECT.
Если пришло «Запрос отклонён: …» — исправь SQL, причина указана в тексте.
Результат урезается лимитом строк; пометка об урезании появляется под таблицей.

**Если скрипт недоступен или падает с ошибкой подключения** — скажи об этом
пользователю прямо и не отвечай на вопрос по данным. Цифр у тебя нет,
придумывать их нельзя.

## Таблица `<SCHEMA>.<TABLE>`

**Одна строка — один штраф.** Это главный факт: `COUNT(*)` сразу даёт число
штрафов, `SUM(<сумма>)` — общую сумму, `AVG(<сумма>)` — средний штраф.
Дедупликация и `DISTINCT` для самой таблицы не нужны.

| Что | Значение |
|---|---|
| Кто выставил | `<колонка>` |
| Кому выставлен | `<колонка>` |
| Сумма | `<колонка>`, `<рубли или копейки>` |
| Дата выставления | `<колонка>` — фильтруй период по ней |
| Дата оплаты | `<колонка или «нет»>` |
| Расшифровка нарушения | `<колонка>` |
| Статус | `<расшифровка значений>` |
| Обязательные фильтры | `<что исключать всегда: отменённые, тестовые>` |
| Проблемы качества | `<периоды с неполными данными, известные дубли>` |

### Колонки

| Колонка | Тип | Смысл |
|---|---|---|
| `<col>` | `<type>` | `<что означает, единицы, бывает ли NULL>` |

## Правила агрегации

- **Главная опасность — JOIN.** Сама таблица гранулярна по штрафу, но как только
  подключается справочник (нарушителей, кодов, расшифровок) с неуникальным
  ключом, строки размножатся и сумма завысится. Агрегируй справочник **до**
  соединения либо убедись, что ключ уникален.
- **Агрегируй в SQL, не тащи сырьё.** `SELECT *` и «посмотрю глазами» —
  неверный путь: лимит строк урежет выборку, и вывод будет сделан по куску
  данных. Сырые строки запрашивай, только когда нужен конкретный штраф.
- **NULL в суммах.** `SUM` и `AVG` молча пропускают NULL, `AVG` делит на число
  непустых значений. Если NULL означает ноль — пиши `COALESCE(<сумма>, 0)`.
- **`COUNT(*)` против `COUNT(col)`** — второй не считает строки с NULL в колонке.
- **Проценты.** Приводи числитель к `numeric` или умножай на `100.0`, иначе
  целочисленное деление обнулит долю. В знаменателе — `NULLIF(x, 0)`.
- **Неполный последний период.** Текущий месяц недобран и выглядит провалом:
  либо исключай, либо предупреждай в ответе.
- **`ORDER BY` обязателен при `LIMIT`** — иначе строки произвольные.
- **Обязательные фильтры из карточки** применяй всегда, даже если о них
  не просили; если фильтр заметно меняет ответ — скажи об этом.

## Графики

`--mode chart` выполняет тот же проверенный SELECT и рисует результат в PNG.
Числа берутся из БД, а не из твоего предыдущего ответа, — переписывать их
в аргументы не нужно и нельзя.

**Раскладка по умолчанию: первая колонка — подписи, остальные числовые —
серии.** Обычный аналитический запрос рисуется без лишних аргументов:

```bash
# Динамика: одна линия
./fines_analyze.sh --mode chart --chart-type line --title "Штрафы по месяцам" \
    --sql "SELECT <месяц>, count(*) FROM <SCHEMA>.<TABLE> GROUP BY 1 ORDER BY 1"

# Топ нарушителей: горизонтальные столбцы, длинные названия не налезают
./fines_analyze.sh --mode chart --chart-type barh --title "Топ-10 нарушителей" \
    --sql "SELECT <нарушитель>, count(*) c FROM <SCHEMA>.<TABLE> GROUP BY 1 ORDER BY c DESC LIMIT 10"

# Разбивка по категориям: накопительные столбцы
./fines_analyze.sh --mode chart --chart-type bar --stacked --title "Штрафы по видам" \
    --sql "SELECT <месяц>, sum(<вид A>), sum(<вид B>) FROM <SCHEMA>.<TABLE> GROUP BY 1 ORDER BY 1"
```

Аргументы: `--chart-type bar|barh|line|pie`, `--title`, `--stacked`,
`--x-column` и `--y-columns` (через запятую) — если раскладка по умолчанию
не подходит.

Выбор типа:

- **line** — динамика во времени. Только по упорядоченному ряду: без
  `ORDER BY` линия соединит точки в случайном порядке и соврёт.
- **bar** — сравнение категорий и помесячные величины.
- **barh** — топ-N, когда подписи длинные (названия организаций).
- **pie** — структура целого, и только если долей немного (до 6-7) и они
  складываются в осмысленное целое. В остальных случаях `bar` честнее.
- **--stacked** — вклад категорий в общую величину по периодам.

Правила:

- **Одна ось — одна единица измерения.** Количество штрафов и сумму в рублях
  на одном графике сравнивать нельзя: столбики в сотнях исчезнут рядом со
  столбиками в миллионах. Рисуй двумя вызовами или приведи к одной шкале
  (доли, индексы, тысячи рублей).
- **График не заменяет цифры.** Ключевые значения назови в тексте: путь к PNG
  пользователь видит не всегда.
- **Рисуй, когда есть что показать** — ряд, распределение, сравнение.
  Два-три числа понятнее словами и таблицей.
- Точек на графике не больше `chart_max_points`; если данные урезаны,
  под графиком появится предупреждение — тогда сузь период или агрегируй
  крупнее, а не выдавай неполную картину за полную.
- Ответ «График не построен: …» означает, что рисовать нечего или тип не
  подходит — причина указана в тексте, исправь запрос или тип.

## Особенности Greenplum

- Версия — GP 6.25, по синтаксису это **PostgreSQL 9.4**. Конструкции из
  PostgreSQL 10+ не поддерживаются; если запрос упал с синтаксической ошибкой
  на современной конструкции — перепиши её классическим SQL.
- **Ключ распределения.** JOIN не по ключу распределения вызывает перекачку
  данных между сегментами и резко замедляет запрос на больших объёмах.
- **Партиционирование.** Если таблица партиционирована по дате, фильтр по
  этой колонке обязателен — иначе сканируются все партиции.
- `EXPLAIN` показывает план; `EXPLAIN ANALYZE` **выполняет** запрос — на
  тяжёлых выборках не используй.

## Когда НЕ использовать этот навык

- Вопрос не про штрафы (аудиторские проверки — это навык `audit_analyzer`).
- Просят изменить данные — доступ только на чтение, откажи.
- Вопрос общий, без привязки к данным, — отвечай сам, без запросов к БД.

## Перед ответом проверь

- JOIN не размножил строки?
- Обязательные фильтры на месте?
- Суммы обёрнуты в `COALESCE`, где это нужно?
- Последний период полный?
- Под таблицей нет пометки об урезании результата?
- Порядок величин правдоподобен?
- Если есть график — на одной оси одна единица измерения, ряд упорядочен,
  а ключевые цифры названы в тексте?

## Формат ответа

- краткий итог и ключевые цифры;
- предупреждения о полноте и качестве данных, если они уместны;
- сам SQL — в конце, в блоке ```sql, для воспроизводимости.
